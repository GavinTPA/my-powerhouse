# skill-plan - How It Works

## The One-Sentence Version

Before you build anything, write down what done looks like - skill-plan makes that a repeatable process.

## Why This Exists

You know how Gary Halbert would never write a sales letter without first knowing exactly who he's writing to and what transformation he's promising? Same principle.

Building skills without a plan is like writing copy without knowing your audience. You might get lucky, but you're probably going to wander. And wandering costs time.

The problem we kept hitting: `tasks/todo.md` had 4 different plans scattered through it. No consistent format. No "what does done look like" section. Plans that were really just task lists, not actual plans.

skill-plan formalizes what was already working (when we did it) into a repeatable process.

## How You Use It

**Say:** "plan this skill for inbox-improver" or "create a plan for newsletter-scheduler"

**What happens:**
1. Claude automatically loads your context (CLAUDE.md, mission-context)
2. Runs semantic search to find related research and prior work
3. Asks you three questions, one at a time:
   - What are you building?
   - What problem does it solve?
   - What does done look like?
4. Generates a complete plan document
5. Saves it to the right place

**Then you can:**
- Hand the plan to new-skill-wizard
- Build directly using the plan as your guide
- Share for review before committing

## The Key Insight

"What done looks like" is not a checklist. It's a picture.

Wrong: "It works and saves files correctly"
Right: "You say 'plan this skill', answer 3 questions, and get a complete planning doc saved to your Knowledge Vault that you can hand to new-skill-wizard."

The picture version tells you when you're actually done. The checklist version leaves wiggle room for "good enough."

## When to Use This

- Starting a new skill from scratch
- Planning an improvement to an existing skill
- After a research swarm, before building
- Anytime you're about to build something non-trivial

## When NOT to Use This

- Quick fixes (one-line changes)
- Obvious improvements that don't need planning
- When you already have a solid plan document
